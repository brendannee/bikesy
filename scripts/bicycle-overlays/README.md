# Bicycle overlay generator

Creates **reviewable, inferred bicycle facility layers** from a local OSM snapshot. It does not certify California bikeway classes, establish legal access, rate safety, or calculate routes. It writes a new directory and never changes Mapbox styles, checked-in map assets, routing costs, or production services.

## Generator package

Keep this directory together: `generate.mjs` uses `rules.mjs`, `relations.mjs`, `geometry.mjs` and the `read_osm.py` bridge. `requirements.txt` pins the reader dependencies; `*.test.mjs` and `fixtures/` provide generator regressions, including XML/PBF end-to-end coverage. No comparison viewer or spatial-analysis packages are required. The virtual environment and generated `build/` outputs are gitignored.

## Run locally

Requires Node 22+ and Python 3.10+ with a compatible Pyosmium wheel. From the repository root:

```sh
python3 -m venv scripts/bicycle-overlays/.venv
scripts/bicycle-overlays/.venv/bin/python -m pip install --only-binary=:all: -r scripts/bicycle-overlays/requirements.txt
node --test scripts/bicycle-overlays/*.test.mjs
node scripts/bicycle-overlays/generate.mjs \
  --input /absolute/path/region.osm.pbf \
  --output build/bicycle-overlays/my-review \
  --surfaces all
```

Dependencies are exact-pinned and local to the ignored virtual environment; nothing is installed globally. `--python /path/to/python` selects another environment with those requirements. The JavaScript generator has no npm dependencies. An existing output directory causes an error; choose a fresh name for each run. Input `.osm` XML and `.osm.pbf` both work. Only an OSM input file is needed; no Docker, database, API credentials, or network requests are used during generation.

`--surfaces all` preserves paved, unpaved, and unknown surfaces in the inferred facility layers. `--surfaces paved` restricts those layers to recognized paved surfaces. In both modes, debug and review outputs retain other surfaces. Missing/unrecognized surface is **unknown**, never silently treated as paved. A custom `--surface-config file.json` can supply disjoint `paved` and `unpaved` arrays; the report records the exact policy. Paved does not mean smooth or comfortable: cobblestones remain paved, and compacted/fine gravel remain unpaved without implying they are unusable. Wood and metal remain unknown under the default pavement policy.

Coordinates are unchanged by default. Optional `--simplify-meters 1` applies local metric Ramer–Douglas–Peucker simplification; `--precision 5` rounds only output coordinates (roughly metre-scale at Bay Area latitudes). These display operations can remove intermediate junctions and collapse short segments. They are unsuitable for routing topology. Simplification rejects ways spanning over two degrees from the local projection origin or above 80° latitude. Five decimals is not a mandatory conversion step.

Use `--strict-geometry` to fail when a candidate way has missing nodes or degenerate geometry. The default retains its record in `debug.jsonl`, reports the issue, and omits it from drawable layers; it never joins across a missing node. Failed runs retain `INCOMPLETE.json`; only runs with `report.json` and **no** incomplete marker are complete.

## Inferred Class I and compatibility displays

The default `--path-policy practical` **does not require `is_sidepath=no`**. `class-I.geojson` includes eligible `highway=cycleway` ways and `path/footway` with `bicycle=designated`, except explicit roadside-track and connector evidence. `highway=cycleway` takes precedence over `footway=sidewalk`; sidewalk context is retained in metadata. Ordinary sidewalks are not promoted by this rule. It is labeled **inferred Class I**, never an official agency designation. Unknown road independence remains visible in confidence/context fields. `path-candidates.geojson` provides the same practical path selection as an explicitly named candidate layer. For the old conservative rule, use `--path-policy strict` in a separate output directory.

The old overlays had a broader meaning: Class I included ordinary `bicycle=yes` paths/footways, including unpaved trails. `legacy-accessible-paths.geojson` preserves that **access-inclusive display group**, also allowing bicycle-permitted paths retagged as tracks/bridleways/pedestrian ways and separately mapped protected tracks. It keeps each feature's actual inferred class and access evidence; it does not certify those paths as Class I. `lanes-and-protected-tracks.geojson` offers an explicitly combined lane/protected display group. Do not render both the combined layer and all constituent layers as separate facilities.

Access restrictions, conditions, lifecycle and geometry filters apply to both displays. Do not fill apparent gaps by restoring prohibited or stale facilities. `--surfaces all` is appropriate for comparison with the actual old files, which include unknown and unpaved surfaces; `--surfaces paved` is a deliberate narrower selection, not an equivalent replacement.

## Cycleway/sidewalk precedence

Explicit `highway=cycleway` now takes precedence over `footway=sidewalk` in classification and path-candidate selection. The original tag remains in debug output, and path candidates carry `sidewalk_context=true`. This does not relax bicycle/access restrictions, lifecycle checks, ordinary sidewalk rules, or crossing/connector exclusions. The three Fort Mason cases are covered by real-tag regression fixtures and an XML/PBF end-to-end test.

## Outputs

Each GeoJSON layer is deduplicated by OSM way ID and sorted numerically. A mixed-facility road can intentionally appear once in more than one layer, with the relevant side-specific facilities attached. No inferred lateral offsets or proximity-based merging are applied.

| File                                         | Contents                                                                                                                         |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `legacy-accessible-paths.geojson`            | Explicit legacy-compatible path/trail/sidewalk/track display with original inferred classes preserved                            |
| `lanes-and-protected-tracks.geojson`         | Explicit combined II + IV display group                                                                                          |
| `path-candidates.geojson`                    | Practical inferred paths from cycleway or designated path/footway tags, with explicit road-context uncertainty                   |
| `class-I.geojson`                            | Practical inferred bicycle paths by default; optional `--path-policy strict` requires independence evidence                      |
| `class-II.geojson`                           | Painted lanes, including flagged advisory/conflicting tags requiring review                                                      |
| `class-III.geojson`                          | Shared-lane markings, bicycle-priority streets, or lower-confidence road route-network fallback                                  |
| `class-IV.geojson`                           | Road-attached `track`, separately mapped cycleway with explicit `cycleway=track`, or roadside cycleway with pedestrian exclusion |
| `other-facilities.geojson`                   | Shared bus lanes and bicycle-accessible paths/cycleways whose class is unresolved                                                |
| `route-network.geojson`                      | Bicycle relation membership, network, route reference/name and roles; review metadata, not access permission                     |
| `review.geojson`                             | Uncertain, conflicting, restricted, inactive, surface-filtered and reference-only records with drawable geometry                 |
| `restricted-or-inactive.geojson`             | Facilities withheld because of access, conditions, lifecycle, steps, area geometry, or motorroad concerns                        |
| `unpaved.geojson`, `unknown-surface.geojson` | Surface review layers, including restricted/inactive facilities                                                                  |
| `debug.jsonl`                                | One record per candidate way: original tags, version, timestamp, geometry or missing-node count, memberships, full rule evidence |
| `report.json`                                | Counts, warning totals/samples, timings, per-process peak memory, input SHA-256, generator hashes, policy and attribution        |

Lean facility layers retain way ID, source timestamp, geometry role, inferred class, facility kind, confidence, side, direction, access status, surface, subtype, buffer/separation, evidence keys, review flags, and route IDs. Full raw tags and access provenance are in debug output. `eligible` only means passing this overlay's filters; it is not a legal-access determination. Unspecified access is not assumed to be a verified permission. `permissive` is retained with an access qualification. Route-network and review layers must not be rendered as an unconditional accessible bike network.

Reports contain local paths, timings, and resource measurements. GeoJSON/debug ordering is deterministic for the same input and options; reports are intentionally run-specific. Counts across layers overlap and should not be added as unique infrastructure mileage. The report's warning totals count occurrences; samples contain up to five way IDs each.

## Classification policy

| OSM evidence                                                  | Treatment                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `cycleway:left/right`, `cycleway:both`, unsuffixed `cycleway` | Explicit side overrides both, which overrides generic. `no` and `separate` suppress fallback. Unsuffixed tagging alone does not prove two lanes.                                                                                                                                                                                                                                           |
| `lane` / `track` / `shared_lane`                              | II-like painted lane / IV-like protected roadside track / III-like shared lane; sides remain independent.                                                                                                                                                                                                                                                                                  |
| `share_busway`                                                | Shared bus-lane category, not an exclusive bicycle lane. `shared_busway` is accepted only as a warned noncanonical alias.                                                                                                                                                                                                                                                                  |
| `cycleway=separate`                                           | Reference to separate mapping, not another facility on the road centerline. Retained in review; the independently mapped way is classified on its own evidence.                                                                                                                                                                                                                            |
| `opposite_lane`, `opposite_track`, `opposite_share_busway`    | Deprecated contraflow evidence retained with a warning. Plain `opposite` conveys access direction only, not a lane.                                                                                                                                                                                                                                                                        |
| `cycleway:*:lane=exclusive/advisory`                          | Preserve lane subtype; advisory is low-confidence and explicitly not exclusively reserved. `cycleway:lanes` and `bicycle:lanes` pipe arrays are different tags, preserved/warned but not parsed into facilities.                                                                                                                                                                           |
| `cycleway:*:buffer`                                           | Buffer metadata alone does not upgrade a lane to IV.                                                                                                                                                                                                                                                                                                                                       |
| `cycleway:*:separation` on a lane                             | Physical separation conflicts are flagged for review; no blind upgrade. `segregated` concerns pedestrians versus bicycles, not protection from cars.                                                                                                                                                                                                                                       |
| `highway=cycleway`                                            | An independent path and a roadside track can use this same tag. Default inference is I-like with road-context uncertainty unless explicit protected-track evidence supports IV-like. Explicit `is_sidepath=no` supports an I-like inference. `is_sidepath=yes` plus `foot=no` supports IV-like; a shared roadside path is I-like in practical mode with explicit road-context uncertainty. |
| `path/footway/...` plus `bicycle=yes`                         | Bicycle-accessible path, not proof of Class I. `bicycle=designated` supports practical I-like inference without requiring `is_sidepath=no`; strict mode still requires independence evidence. Ordinary footway/path sidewalks remain a separate unresolved category; explicit `highway=cycleway` is not overridden by `footway=sidewalk`.                                                  |
| `bicycle_road=yes`, `cyclestreet=yes`                         | III-like bicycle-priority street on an ordinary road.                                                                                                                                                                                                                                                                                                                                      |
| `lcn/rcn/ncn/icn=yes`, active bicycle route membership        | Separate network metadata; III-like fallback only on an ordinary road without stronger facility evidence. Membership alone does not prove signs exist.                                                                                                                                                                                                                                     |
| `access`, `vehicle`, `bicycle`, directional forms             | Bicycle overrides vehicle, which overrides general access; directional forms take precedence within each mode. Explicit `bicycle=yes` can override `access=no`. Private, dismount, use_sidepath, destination/customer/permit restrictions stay distinct and are withheld.                                                                                                                  |
| `*:conditional` affecting bicycle/access/oneway/cycleway      | Preserved unevaluated and withheld from facility layers. No claim that it is open now. Motorcar-only conditions do not suppress bicycle facilities.                                                                                                                                                                                                                                        |
| Proposed/construction/disused/abandoned ways                  | Retained for review, withheld from active facilities. No proposed-route III fallback.                                                                                                                                                                                                                                                                                                      |
| `highway=steps`, bicycle ramps                                | Review only; ramp evidence remains in raw tags. No stair-to-bike-path conversion.                                                                                                                                                                                                                                                                                                          |
| `area=yes`                                                    | Review only; perimeter is not silently promoted to a linear bikeway.                                                                                                                                                                                                                                                                                                                       |
| `motorway`, motorway links, `motorroad=yes`                   | No route-network permission override; candidate facilities require manual review.                                                                                                                                                                                                                                                                                                          |

Left/right refers to OSM way direction. Side-specific `cycleway:*:oneway` overrides normal direction; otherwise road oneway or right-hand-traffic side conventions are used. A separate path uses bicycle oneway before general oneway. `oneway:bicycle=no` does not invent an opposite-side facility. Unresolved generic direction is explicit. Less-common `cycleway:forward/backward` facility values are retained and warned for manual review; `bicycle:forward/backward` access and side-specific direction are interpreted. Defaults target the Bay Area, not left-hand-traffic countries.

Surface, lane subtype, buffer, separation and oneway attributes use side → both → generic precedence. Surface then falls back to the way's surface with its source key recorded. Side-specific surface may differ from the motor road.

Bicycle route and bicycle route-master relations are read before ways and nested memberships expanded up to eight levels. Direct and inherited networks/roles are retained; roles do not change traffic legality. Cycles and missing/non-bicycle nested relations are counted. Mountain-bike routes are deliberately not treated as bicycle-road route evidence. Relation member, relation and candidate-way limits fail explicitly instead of producing silently truncated success. Increase `--max-memberships`, `--max-relations`, or `--max-features` only after reviewing memory needs. Incomplete extracts can omit relation children or ways; this tool does not download them.

## How this replaces the old conversion workflow

The described older process selected XML subsets for paths, lanes and routes, used surface filters, converted/merged subsets, and rounded coordinates. The actual local GeoJSON files retain many unpaved and unknown surfaces, so the comparison uses their real contents rather than assuming the filters removed them. That loses side-specific detail, mixes access with facility designation, misses protected roadside tracks, and can silently erase useful unpaved/unknown infrastructure.

This tool makes two sequential Pyosmium passes directly over the original XML/PBF: bicycle relations, then ways with node coordinates. JavaScript handles one centralized policy and emits all layers from the same candidate records. There are no intermediate XML subsets, repeated format conversions, global CLI dependencies, or lossy geometry changes by default. Pyosmium's node-location cache scales with input nodes; candidate geometries and route memberships are held in Node memory. This is a bounded regional-extract workflow, not a planet-file pipeline.

The existing San Francisco style is hosted in Mapbox and its checked-in legend only lists Classes I–III. This script intentionally does not wire generated files into that style. Before replacing an overlay, inspect protected tracks and ambiguous paths, decide how to present Class IV and shared bus lanes, make unknown surfaces visible, and validate a sample against imagery/local agency inventories. Do not label inferred classes as officially designated without that verification.

Useful next mapping/review fields include `width`/usable cycleway width, `smoothness`, `lit`, `maxspeed`, `traffic_sign`, parking/door-zone context, physical separation, crossing treatments, bridge/tunnel/layer, and current construction status. Preserve them as distinct evidence rather than collapsing them into a single safety score. Spatial conflation of duplicated road-track tagging versus separately mapped cycleways requires a separate reviewed workflow; distance alone is not sufficient to delete a feature.

## Actionable tagging and map recommendations

1. Preserve `highway=cycleway` or a surveyed `path/footway` plus `bicycle=designated` as path-facility evidence. Use `bicycle=yes` for access permission only; do not promote every accessible footpath to bikeway status.
2. Record actual `is_sidepath` context when known. Missing context is a review flag, not a reason to hide designated paths. Shared roadside paths and exclusive roadside tracks need separate cartographic treatment.
3. Prefer side-specific `cycleway:left/right/both=lane/track/shared_lane/share_busway`. Use `separate` where the facility is mapped independently; do not duplicate it on the road centerline.
4. Record `cycleway:*:lane=exclusive/advisory`, buffer and physical separation independently. Correct noncanonical values only from verified evidence; a buffer or `segregated=yes` alone does not prove protection from motor vehicles.
5. Fill actual side-specific surface and access/conditional/direction tags. Show unknown surfaces distinctly instead of assuming pavement. Retain route relations as network metadata, not proof of legal access or signs.
6. Review named corridor samples and local inventories before replacing the hosted style. Give protected tracks and shared bus lanes distinct legend treatment. Current closures are a separate data concern: this snapshot generator does not fetch park alerts.
